# Тестовая ЮKassa

Тестовая интеграция подготовлена после выпуска основы заказов `4eede30`.
Выпуск кода и активация на сервере выполняются отдельно: для тестового магазина
нужны env-настройки backend/frontend, точные правила Caddy и подписка на webhook.

## Реализовано

- Только тестовые ключи (`test_`), режим `YOOKASSA_MODE=test` и отдельное
  `PAYMENTS_ENABLED=true`. Боевые ключи и режим live кодом отклоняются.
- До создания платежа GET `/v3/me` подтверждает ID магазина, `test=true` и
  доступность. HTTPS API фиксирован; секреты не попадают в браузер или ошибки.
- Закрытая таблица `shop_payments`: одна попытка на заказ. Ключ идемпотентности
  и неизменяемое тело запроса сохраняются до сетевого вызова. При потере ответа
  повторяется тот же POST, а после сохранения providerId выполняется GET.
  Через 23 часа неизвестную попытку повторять нельзя: у провайдера гарантия
  идемпотентности ограничена 24 часами.
- `capture=true`, подтверждение redirect, только серверная сумма. Возврат использует
  проверенный origin из PAYMENT_ALLOWED_ORIGINS либо PAYMENT_RETURN_ORIGIN.
  Принимаются лишь известные HTTPS URL оплаты yoomoney.ru.
- Статус проверяется через GET платежа с полным сопоставлением ID, магазина,
  суммы, RUB, metadata заказа/попытки и test=true. Уведомление и возврат браузера
  сами по себе не подтверждают успех.
- Конкурентные запросы/уведомления не понижают финальный статус. Webhook,
  пришедший до сохранения providerId, находит свою попытку по metadata и всё
  равно перепроверяет её через API. Неизвестные уведомления не вызывают запросов
  провайдеру. Сбой проверки даёт 503 для повторной доставки.
- Общая отмена заказа запрещена после начала платёжной попытки. Это исключает
  отмену локальной записи одновременно с успешной оплатой. Отмена платежа
  подтверждается только фактическим статусом провайдера.
- Успех теста — отдельный `test_paid`, не `paid`. Такой заказ открывает только
  специально помеченный testOnly оригинал; обычные платные файлы недоступны.
  Живые продажи и возвраты — отдельный этап.
- Next BFF использует HttpOnly сессию владельца и проверяет Origin для POST.
  Отдельный секрет защищает внутренний webhook bridge; браузерный JWT и ключ
  ЮKassa туда не передаются. Внешний webhook на production открыт адресно в Caddy.
- Стеклянный экран оформления: «ЮKassa», неактивные SberPay и Apple Pay,
  тестовое предупреждение, возврат с проверкой статуса, ручная повторная проверка.
- После серверного подтверждения paid/test_paid из корзины убираются позиции
  этого заказа, другие товары сохраняются. Последние 200 обработанных заказов
  отмечаются в локальном хранилище, чтобы повторный просмотр старого заказа
  не удалял заново добавленные товары. Новый состав получает новый checkoutKey.
  Подпись корзины учитывает включённый тестовый режим оплаты.
- «Купить» в каталоге и на странице товара открывает общее стеклянное окно оплаты.
  Оно создаёт отдельный заказ только на выбранный товар, не изменяя состав корзины.
  Checkout key сохраняется по пользователю и товару для безопасного повтора.
  Уже купленный товар открывает скачивание и «Мои покупки» без нового платежа.
  После ЮKassa возврат ведёт на обычный завершённый заказ и историю.
- Публичное purchaseAvailable вычисляется сервером: в текущем test-режиме нужны
  включённые заказы/платежи и готовый testOnly оригинал. Обычные товары показывают
  неактивную кнопку; POST вручную также не разрешает купить неподготовленный файл.

## Локальный просмотр — Windows, PowerShell

Предварительно запустить существующие PostgreSQL и Mailpit через compose.auth.yaml.
Секреты тестового магазина уже сохранены в игнорируемом `.local/payments/backend.env`;
в нём остаются PAYMENTS_ENABLED=false и YOOKASSA_MODE=test. Для процесса тестового
запуска флаг включается отдельно, исходный файл не переписывается.

```powershell
& .local/tools/node-v22.23.4-win-x64/node.exe scripts/local-auth.cjs start --payments-test
```

Затем в другом локальном PowerShell:

```powershell
& .local/tools/node-v22.23.4-win-x64/node.exe scripts/local-checkout-preview.cjs --build
& .local/tools/node-v22.23.4-win-x64/node.exe scripts/local-checkout-preview.cjs
```

Первый backend-запуск создаёт только локальный bridge secret в игнорируемом
`.local/payments/frontend.env`; API-ключ ЮKassa frontend не получает.
Адрес сайта: http://127.0.0.1:3100. Почта локальных регистраций: Mailpit,
http://127.0.0.1:8026. Никаких настоящих карт; использовать тестовые данные
из документации провайдера.

## Проверено 15.11.2026

- 39 backend + 73 frontend автоматических теста, TypeScript и сборка Next.
- Настоящие локальные Strapi/PostgreSQL: заказы, перенос при merge, конкуренция,
  потеря ответа API, поддельные/повторные уведомления, неверная сумма, отмена,
  запрет выдачи платного файла после test_paid. Внешний провайдер в этой проверке
  подменён, все созданные записи удалены, предварительная копия БД сохранена.
- Через настоящий локальный Next BFF создан один платёж в реальном тестовом
  магазине ЮKassa: ответ pending, повторный POST вернул тот же платёж, статус
  перепроверен через API. Реальные деньги не списывались. Локальная служебная
  учётка, заказ и попытка удалены после проверки; тестовая запись провайдера
  остаётся pending до его штатного истечения.
- Автоматизация браузера остановилась из-за неопределённого URL. Hosted-оплату
  и возврат затем вручную проверил пользователь (см. итог ниже).

Обновление после ручной проверки 15.11: пользователь прошёл hosted-оплату с
тестовой картой 5555…4477 и 3-D Secure. Прямой GET API подтвердил succeeded,
test=true и 299 RUB; магазин, metadata и сумма сопоставлены с локальным заказом.
После возврата пользователь прислал страницу заказа «Тестовая оплата подтверждена».
Чтение БД подтвердило test_paid/succeeded: штатный frontend BFF проверил и
сохранил результат. Агент вручную состояния БД не устанавливал.

## Проверено 16.11.2026 и оставшиеся этапы

Пользователь подтвердил полный production-путь: тестовая оплата, скачивание на
странице заказа и повтор из кабинета. Три события webhook настроены на
https://themesphone.ru/api/payments/yookassa/webhook. Прямой CMS API закрыт.

Для доработки корзины и «Купить» пройдены 42 backend + 82 frontend tests,
TypeScript/build и изолированная интеграция PostgreSQL/Strapi с подменённым
провайдером: исключение уже оплаченного из суммы, запрет второго платежа,
старые покупки вне первой страницы, одиночный заказ, история и точные байты
скачивания. Временные записи удалены. Новые правила Caddy/env не требуются.

Ручная проверка нового окна «Купить» выполняется после его выпуска. Неуспешная
hosted-оплата и пользовательский повтор остаются отдельной проверкой; серверные
отмена/повторы уже проверены интеграцией. До настоящих продаж необходимы
независимое резервирование/восстановление S3, оформление продавца, чеки, возвраты
и отдельный live-режим. Боевые ключи пока запрещены.
