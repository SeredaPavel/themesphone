# Серверные заказы — этап перед подключением оплаты

Основа заказов подготовлена 15.11.2026 в `devcodex`. Выпуск кода не включает
оформление и оплату: они активируются отдельно. Тестовый доступ к ЮKassa проверен
чтением `GET https://api.yookassa.ru/v3/me`: магазин подтвердил `test=true` и
совпадение ID. Платежи во время проверки не создаются.

## Контракт заказа

- Новая закрытая коллекция `shop_orders` без Draft & Publish. Старые `orders`
  сохраняются для истории и объединения профилей, их универсальные REST-маршруты
  сняты. Значение `paid` из старой таблицы не открывает оригиналы.
- `POST /api/shop-orders`: только `items` (1–30 различных `documentId`) и
  `checkoutKey` (UUID v4). Цену, владельца, валюту и состояние клиент передать не
  может. Пользователь определяется из JWT; проверяется свежая запись аккаунта.
- Принимаются опубликованные платные товары с корректной ценой и зарегистрированным
  готовым оригиналом. Превью не становится покупаемым оригиналом.
- Текущий `wallpaper.price` в Strapi хранит целые рубли. Сервер переводит их в
  целые копейки без дробных вычислений; сохраняет название, цену, `documentId` и
  внутренний ID оригинала. Ответ клиенту не содержит внутренних полей хранения.
- Цена и состав фиксируются на 24 часа. Новая цена товара не меняет старый заказ.
  Повтор того же запроса возвращает тот же заказ; изменённый состав с прежним
  ключом даёт 409. На аккаунт допускается до 20 действующих неоплаченных заказов.
- `GET /api/shop-orders/:id`, `GET /api/shop-orders?page=1` и
  `POST /api/shop-orders/:id/cancel` работают только с заказами текущего владельца.
  Чужой и отсутствующий заказ возвращают одинаковый 404. Универсального update
  нет. Пагинация — по 20 записей; фильтры, populate и смена владельца не принимаются.
- Создание, чтение, отмена и OAuth-объединение используют блокировку пользователя.
  Заказы обеих таблиц переносятся на основной аккаунт в транзакции объединения;
  архивный профиль не может создать новый заказ.

## Frontend

Next.js передаёт Strapi только JWT из HttpOnly cookie текущего пользователя.
Сервисный `STRAPI_API_TOKEN` при оформлении больше не используется. Изменяющие
запросы требуют разрешённый Origin, ответы не кешируются. Старый
`/api/checkout/pay` отвечает 503 и больше не устанавливает `paid: true`.

Корзина хранит `documentId`, переживает повреждённое/недоступное localStorage,
не затирает сохранённые товары при первом рендере. Старые записи без documentId
остаются видимыми, но перед оформлением предлагается добавить их заново.
Отменённый или просроченный заказ можно оформить заново из корзины с новым ключом.

Экран оформления использует общие стеклянные формы и анимации. Кнопки:
«ЮKassa», «SberPay (в разработке)», «Apple Pay (в разработке)». Пока все способы
оплаты неактивны, это прямо пояснено до нажатия. Оригиналы после создания заказа
не выдаются.

## Локальная проверка — Windows, PowerShell

```powershell
docker compose --env-file .local/auth/backend.env -f compose.auth.yaml up -d --wait
& .local/tools/node-v22.23.4-win-x64/node.exe --experimental-strip-types scripts/check-local-orders.cjs
```

Скрипт допускает только `127.0.0.1:5434/themesphone_auth_dev`, сохраняет и
проверяет pg_dump перед изменением схемы. Создаёт свои временные товары, пользователей,
метаданные оригиналов и заказы, затем удаляет их. Нет обращений к S3, внешней
почте, OAuth-провайдерам или ЮKassa. Проверяются реальные HTTP-маршруты Strapi,
Next BFF, конкурентные повторы, серверная сумма, чужие заказы и перенос при merge.

Для обычного локального запуска API заказов предусмотрен флаг `--orders` у
`scripts/local-auth.cjs start` (можно добавить `--oauth`); без флага заказы выключены.
Реальные платежи этот запуск не включает.

Секреты тестового магазина лежат только в игнорируемом
`.local/payments/backend.env`. Из примера `payments.env.example` в Git попадают
только имена переменных. Проверка ключей:

```powershell
& .local/tools/node-v22.23.4-win-x64/node.exe backend/scripts/check-yookassa.cjs
```

## Следующий этап — тестовая оплата

Нужны создание платежа по сохранённому заказу, ключ идемпотентности провайдера,
проверка статуса через API ЮKassa, сверка суммы/валюты/магазина/метаданных заказа,
устойчивость к повторным и поддельным webhook, отмене и сбою сети. Возврат браузера
сам по себе не подтверждает оплату. Тестовые платежи отделяются от реальных прав
на платный оригинал. Затем — безопасная выдача по подтверждённому праву.

До этого `PAYMENTS_ENABLED=false`. `ORDERS_ENABLED` по умолчанию тоже выключен;
его включение на production в backend и frontend потребует отдельного выпуска
и точного разрешения Next BFF в Caddy. Пока флаг выключен, кнопка оформления
также неактивна и поясняет ограничение заранее. Текущие правила Caddy, Compose, серверные секреты и соседние
проекты на данном этапе не менялись. Готовность реальных продаж дополнительно
требует оформления продавца/магазина и отдельного резервирования S3.

Документация провайдера: [формат API](https://yookassa.ru/developers/using-api/interaction-format),
[тестирование](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).
